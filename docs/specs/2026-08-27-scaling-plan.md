# 다수 사용자로 가는 계획

한 사람이 쓰던 것을 여러 사람이 동시에 쓰게 만드는 순서. 각 단계는 **지금
무엇이 막고 있는지**로 정해져 있고, 하나를 치우면 병목이 다음으로 옮겨 간다.

## 측정한 사실

| | 값 | 어떻게 |
|---|---|---|
| 서버 프로세스 메모리 (임베딩 켬) | **1,326 MB** | 기동 후 RSS |
| 서버 프로세스 메모리 (`SEARCH_EMBEDDINGS=off`) | **172 MB** | 같은 방법 |
| ⇒ 임베딩 모델(KURE-v1)이 차지하는 몫 | **약 1.15 GB** | 차이 |
| 지금 uvicorn 워커 | 1개 | 기동 명령 |
| 실질 동시 면접 | **1명** | 아래 A 참고 |

Live API 쪽 한도는 커넥션 약 10분, audio-only 세션 15분, 컨텍스트 128k다.
**동시 세션 수는 프로젝트 tier에 따라 다르고 공개돼 있지 않다** — AI Studio
대시보드에서 확인해야 하고, 그 값이 결국 동시 사용자 수의 천장이 된다.

## 병목이 옮겨 가는 순서

```
지금        이벤트 루프가 막힘        → 동시 면접 1명
A 이후      CPU · 메모리 · Live 쿼터  → 동시 면접 3~5명 (단일 워커)
C 이후      VM 메모리 여유            → 5~10명
E 이후      DB · Live 쿼터            → 수십 명
```

---

## A. 이벤트 루프 해방 — 동시성의 전제 (반나절)

**막고 있는 것.** ADK는 동기 툴 함수를 이벤트 루프에서 그대로 호출한다
(`function_tool.py:338` — `to_thread`도 executor도 없다). 그런데 우리 툴 둘 다
동기이고 안에서 무거운 일을 한다.

- `ask_question` → 파볼 곳 추출(Grok) **약 2초**
- `search_knowledge` → 임베딩 검색, 캐시 미스면 인덱스 재구축

그래서 **한 사람의 2초가 서버 전체를 멈춘다.** 다른 사람의 오디오도, HTTP
요청도. 사용자가 한 명이라 안 보였을 뿐이다.

**할 일**
1. 두 툴을 `async def`로 바꾸고 블로킹 구간만 `asyncio.to_thread`로 민다
   (Grok 호출, 임베딩 인덱스 빌드·검색). 툴 시그니처는 그대로라 ADK의 선언
   생성에는 영향이 없지만, async 툴이 live 경로에서도 await되는지 설치된
   소스로 확인할 것
2. `_cached_knowledge_index`의 `lru_cache(maxsize=2)`를 16 정도로. 동시
   사용자가 셋만 돼도 매 검색이 캐시 미스가 되어 인덱스를 다시 만든다

**효과.** 동시 면접 1명 → 여러 명. 이것이 없으면 아래 어느 것도 의미가 없다.

**검증.** 동시 2~3 세션에서 오디오가 끊기지 않고 필러가 제때 나오는지. 로그의
`토큰 사용` 줄로 각 세션이 독립적으로 진행되는지.

---

## B. 돈이 새지 않게 — 유료 서비스의 최소 요건 (반나절)

1. **크레딧 이중 차감 방지.** `charge()`가 잔액을 읽고 쓰는데 SQLite에서 읽기가
   쓰기 잠금을 잡지 않는다. 두 탭에서 동시에 시작하면 둘 다 통과할 수 있다.
   `BEGIN IMMEDIATE`로 트랜잭션을 열거나 조건부 INSERT로 바꾼다
2. **면접 시간 서버 하드캡.** 지금 면접을 끝내는 것은 지원자의 종료 버튼뿐이다
   (`tools.py`에 명시된 설계 결정). Live API가 턴마다 누적 맥락을 다시 과금하는
   구조라, **상한이 없으면 1회 원가에 천장이 없다.** 설계 결정을 뒤집는 일이라
   사용자 판단이 필요하다
3. **답변 0인 면접 환불.** 실수로 시작하고 바로 나온 경우 크레딧이 그대로
   나간다. 판정 근거(전사에 지원자 발화가 있는가)와 환불 경로는 이미 있다

**효과.** 사고 하나가 수십 달러가 되는 경로를 닫는다. 결제를 붙이기 전에
끝나 있어야 한다.

---

## C. 배포 — 사용자가 들어올 수 있게 (하루)

**형태.** 단일 VM, 단일 프로세스. 리버스 프록시가 HTTPS를 맡고 FastAPI 하나가
API와 프론트를 같이 서빙한다.

1. **프론트를 같은 오리진에서.** `web/dist/`를 FastAPI에 mount한다. 그러면
   vite 프록시가 필요 없고 `APP_BASE_URL`을 비울 수 있다 — 개발에서만 쓰던
   설정이 배포에서 사라진다
2. **HTTPS.** Caddy(자동 인증서)가 가장 손이 덜 간다. nginx + certbot도 된다
3. **프로세스 관리.** systemd 유닛으로 재시작·부팅 시 자동 기동
4. **환경변수 조정** — `SERVER_BASE_URL=https://도메인`, `COOKIE_SECURE=1`,
   `SESSION_SECRET` 고정. 카카오 콘솔에 배포 콜백 URI를 **추가**한다(로컬 것은
   지우지 말 것 — 여러 개 등록된다)
5. **`SEARCH_EMBEDDINGS=off`를 VM 기본으로.** 1.15 GB를 아끼고 BM25 검색으로
   돈다. 메모리가 넉넉하면 켜면 되고, 이 스위치는 이미 있다

**효과.** 홍보 영상에 링크를 넣을 수 있는 상태.

**주의.** 기동 시 마이그레이션(`daedam.db.migrate`)은 단일 인스턴스라 안전하다.
워커를 늘리는 순간 그 호출을 빼고 배포 파이프라인에서 한 번만 돌려야 한다.

---

## D. 관측 — 숫자로 판단할 수 있게 (반나절)

- 이미 붙인 `토큰 사용` 로그를 면접별 원가로 집계한다. **크레딧 가격을 확정할
  유일한 근거**이고, 지금 추정치의 3배 폭을 좁힌다
- 동시 세션 수와 실패율을 남긴다 — Live 쿼터에 부딪히는지 판정하려면 필요하다
- Deep Research 실원가도 건별로 남긴다($1~3은 Google의 추정치다)

**효과.** 요금표 확정. 그리고 다음에 무엇을 늘려야 하는지가 추측이 아니게 된다.

---

## E. 규모 확장 — 필요해지면 (2~3일)

여기까지는 사용자가 실제로 늘어난 뒤에 한다. 미리 하면 검증할 수 없다.

1. **PostgreSQL.** `DATABASE_URL`만 바꾸면 되도록 만들어 두었고 드라이버도 들어
   있다. ADK가 면접 중 턴마다 세션 이벤트를 쓰므로 동시 면접이 늘면 SQLite
   쓰기 경합이 먼저 온다
2. **프로세스 메모리 상태 외부화.** 지금 워커를 늘리면 **깨진다** — 필러 커넥션
   레지스트리(`fillers._connections`)와 준비·평가 진행 상태가 프로세스 안에
   있어서, 콜백이 A 워커에서 돌고 소켓이 B 워커에 있으면 필러가 안 나간다.
   Redis나 DB로 옮겨야 워커를 늘릴 수 있다
3. **임베딩 분리.** 검색 품질 때문에 켜야 한다면 별도 프로세스로 빼서 워커들이
   공유한다. 워커마다 1.15 GB를 물면 메모리가 먼저 바닥난다

**효과.** 동시 수십 명. 다만 그 전에 Live API 동시 세션 쿠터가 먼저 걸릴 수
있으므로 D에서 실측한 뒤에 판단한다.

---

## 순서와 이유

**A → B → C → D → E.**

A가 먼저인 것은 그것이 없으면 "동시 사용"이라는 말 자체가 성립하지 않기
때문이다. B가 그다음인 것은 사용자가 들어오기 전에 닫아야 하는 구멍이기
때문이고, C는 사용자가 들어오는 문이다. D는 C 직후에 붙어야 첫 사용자들의
데이터로 요금을 정할 수 있다. E는 D의 숫자를 보고 판단한다.

A·B는 하루, C는 하루. **홍보 영상까지 남은 기간 안에 A~D가 들어간다.**

## 진행 현황 (2026-08-27)

A·B와 C의 코드 몫은 끝났다. VM 사양이 나오면서 계획이 한 번 크게 바뀌었다.

**임베딩을 Gemini API로 옮겼다.** VM이 2 vCPU·GPU 없음이라 로컬 모델 값이
감당되지 않았다 — 인덱스 100청크 **50초**, 질의 0.82초(2 vCPU 실측). API로는
2.2초와 0.47초다. 메모리도 1,326 MB → **172 MB**로 떨어졌다. 그래서
`SEARCH_EMBEDDINGS=off`로 물러설 이유가 사라졌고, 검색 품질을 지키면서 CPU
문제가 없어졌다. 임계값(코사인)은 모델에 딸린 값이라 실제 카드로 다시 쟀다.

**A 완료.** 툴을 async로 바꾸고 블로킹을 `to_thread`로 밀었다. 판정: 인덱스
빌드 1.78초가 도는 동안 다른 요청 34건이 최대 12ms로 응답했다.

**B 완료.** 이중 차감(BEGIN IMMEDIATE), 하드캡(예산 2배 백스톱), 답변 없는
면접 환불.

**C의 코드 몫 완료.** 프론트를 같은 오리진에서 서빙하고, `deploy/`에 systemd
유닛과 Caddyfile을 넣었다. 절차는 `docs/deploy.md`.

**하다가 찾은 것 하나** — ADK의 `get_fast_api_app`이 **인증 없는 에이전트
API를 통째로 열어 두고 있었다**. `/run`·`/run_sse`·`/run_live`로 누구나
에이전트를 돌려 우리 돈을 쓸 수 있었고, 세션 API로 남의 면접 대화를 읽고
지울 수 있었다(실측). 우리가 쓰지 않는 것이라 맨 FastAPI로 바꿔 라우트 27개를
없앴다.

## 사람 손이 필요한 것

1. **도메인 구입과 DNS** — A 레코드가 VM 공인 IP를 가리켜야 한다
2. **Azure 네트워크 보안 그룹에서 80·443 열기** — Caddy가 인증서를 받으려면 80이
   필요하다
3. **VM에 배포** — `docs/deploy.md` 절차. 저장소 접근과 sudo가 필요하다
4. **카카오 콘솔에 배포 콜백 추가** — `https://{도메인}/api/auth/kakao/callback`
5. **AI Studio에서 Live API 동시 세션 한도 확인** — 공개돼 있지 않고, 그 값이
   동시 사용자 수의 실제 천장이다

## 남겨 둔 것 (D·E)

- **D 관측** — 토큰 로그를 면접별 원가로 집계. 첫 사용자 데이터가 있어야 뜻이
  있으므로 배포 뒤에 한다
- **녹음 보관 정책** — 20분 면접 한 판이 73 MB(pcm+wav)라 51 GB면 약 700판이다.
  `mic.pcm`은 `mic.wav`를 만든 뒤 지워도 되고(절반), 오래된 녹음 정리 기준도
  필요하다
- **E 규모 확장** — PostgreSQL, 상태 외부화, 워커 다중화. D의 숫자를 보고 판단
