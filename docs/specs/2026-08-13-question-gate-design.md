# 질문 게이트 — 모든 질문을 툴로 통과시키기

2026-08-13 · 상태: 승인됨, 미구현

## 왜

면접관이 한 주제에 꼬리질문을 계속 물면서 `get_next_question`을 충분히 부르지
않는다. 실측: 9분 면접에서 뼈대질문이 2~3개만 나갔고, 5분 40초 동안 자기소개
단계를 벗어나지 못한 회차도 있었다. 시간 예산으로 단계를 미는 장치를 넣어
단계 전환은 해결됐지만, **한 단계 안에서 준비된 질문이 안 나가는 것**은 그대로다.

시스템 프롬프트로 누르는 것은 답이 아니다. 대화가 길어질수록 프롬프트의 영향이
약해진다 — 매 턴 다시 실리지만 그 뒤에 쌓인 대화가 훨씬 길어지기 때문이다.
반면 **툴 선언과 툴 출력은 매 호출마다 새로 도착한다.** 그래서 페이싱 판단을
프롬프트가 아니라 툴 쪽으로 옮긴다.

이번 주 코칭 세션 주제 — "AI의 유연함을 충분히 가져가면서 어떻게 불확실성을
줄여 강제할 것인가" — 에 대한 대표님 피드백에서 나온 설계다. 모델은 여전히
자기 꼬리질문을 스스로 만들고, 서버는 그 질문이 나갈 값어치가 있는지만 정한다.

## 툴 계약

`get_next_question`을 `ask_question`으로 교체한다. 모델이 질문을 하려면 이
한 줄을 지나야 한다.

```python
ask_question(
    question: str,                            # 모델이 물으려는 질문 문장
    tag: str,                                 # 주제 태그 (세션 어휘 enum)
    kind: Literal["follow_up", "new_topic"],
    priority: int,                            # 1~5, 아래 척도
) -> dict
```

반환은 경로와 무관하게 한 모양이다.

```python
{"ask": "<실제로 물어야 할 질문 문장>", "stage": "직무역량", "note": "..."}
```

- 승인 → `ask`는 모델이 넘긴 문장 그대로
- 반려·새 주제 → `ask`는 풀의 질문, `note`가 이유를 설명

모델이 지킬 규칙이 한 줄로 줄어든다: **"`ask`에 담겨 온 것을 물어라."** 승인과
반려로 반환 모양이 갈리면 모델이 매번 분기를 판정해야 하는데, 그 판정이야말로
대화가 길어질수록 흐려지는 부분이다.

면접이 끝날 때만 예외로 `{"done": True, "note": ...}`를 돌려준다 (하드캡·질문
소진). 지금 `get_next_question`과 같다.

`kind`는 필수 enum이다. `bool`로 두면 모델이 값을 안 정했을 때 "새 주제" 쪽으로
흘러 카운터를 통째로 빠져나간다 — 오신고의 손해가 한쪽으로만 크다.

## 판정

**매 호출마다 새로 계산한다. 미리 정해둔 일정이 아니다.**

```
1. 하드캡을 넘었으면        → done, 마무리 지시 (현행 유지)
2. 시간이 단계를 앞질렀으면  → 단계 끌어올림 (현행 유지)

3. kind == "new_topic"
     → 풀에서 배달 (tag로 고름), 자유 질문 카운터 0

4. kind == "follow_up"
     자유 질문 카운터 ≥ 3    → 반려 (상한)
     next_q = 단계를 걸어 올라가며 뽑은 다음 뼈대질문 (tag 없이, 현행 루프 재사용)
     next_q 가 없으면        → 승인 (비교 대상이 없다)
     문턱 = next_q.priority + 2 − 자유 질문 카운터
     priority ≤ 문턱         → 승인, 카운터 += 1
     아니면                  → 반려

   반려 = next_q 배달, 카운터 0,
          note에 "이 주제에 시간을 많이 썼습니다"
```

비교 대상은 **그 시점에** 다시 뽑는다. 사이에 시간이 단계를 밀었으면 다른 단계의
질문이 나오고 문턱도 달라진다. 다음 뼈대질문이 핵심 검증(1)일 때:

```
자유 질문 0개 → 문턱 3
자유 질문 1개 → 문턱 2
자유 질문 2개 → 문턱 1
자유 질문 3개 → 불가
```

문턱이 한 칸씩 올라가므로 고정 문턱과 달리 스스로 끝난다. 고정 문턱은 모델이
매번 `priority=1`을 신고하면 영원히 빠져나간다.

**그 위에 상한 3을 얹는다.** 문턱만으로도 끝나기는 하지만, 남은 뼈대질문이
곁가지(4~5)뿐이면 자유 질문이 여섯 개까지 나갈 수 있다. 준비된 질문 사이에
자작 질문이 그렇게 길게 끼는 것은 어떤 경우에도 면접이 아니다. 상한은 문턱과
무관하게 먼저 걸린다.

여기서 따라 나오는 성질 둘:

- **단계가 진행될수록 문턱이 낮아진다.** 중요한 질문이 이미 나갔으면 남은 건
  곁가지뿐이고, 그때는 파던 자리를 더 파는 편이 낫다. 별도 규칙 없이 맞는다.
- **다음에 물을 것이 중요할수록 조건이 까다로워진다.** 자유 질문의 개수 상한은
  늘 3이지만, 핵심 검증(1)이 기다리고 있으면 세 번째 자유 질문은 `priority=1`로
  신고해야만 통과한다. 곁가지(4)만 남았으면 셋 다 무리 없이 통과한다. 상한이
  개수를 막고 문턱이 값어치를 묻는다.

### 카운터는 태그와 무관하다

세는 것은 주제가 아니라 **마지막 뼈대질문 이후 모델이 자기 질문을 몇 개 했는가**
이다. 꼬리질문마다 태그가 달라지므로 "현재 주제"라는 상태는 유지할 수 없고,
유지할 필요도 없다.

이 정의가 교차검증을 대신한다. 모델이 할 수 있는 위험한 거짓말은 하나뿐인데 —
새 주제를 `follow_up`으로 신고해 준비된 풀을 건너뛰는 것 — 태그로는 잡히지
않는다(새 주제니 태그도 새것이라 "태그가 바뀐 꼬리질문"과 구분되지 않는다).
카운터는 그것을 그대로 잡는다. 자기 질문을 계속 하면 횟수가 쌓여 문턱이 올라가고
결국 풀 질문이 밀려 들어온다.

`tag`는 새 주제를 고를 때만 쓰이고(현행 `pool.next`와 동일), 꼬리질문일 때는
로그에만 남는다.

## priority 척도

`Question.priority`의 뜻만 바꾸고 필드는 늘리지 않는다. 지금은 단계 안 출제
순서(중복 없는 1,2,3…)이고, 앞으로는 절대 중요도다. 동점을 허용한다.

| 값 | 기준 |
|---|---|
| 1 | 핵심 검증 — 못 들으면 합격 판단이 안 서는 질문 |
| 2 | 근거 확인 — 내세운 성과·판단의 근거, 본인이 맡은 몫 |
| 3 | 역량의 폭 — 다른 각도에서 같은 역량 재확인 |
| 4 | 맥락 보완 — 배경·동기·협업 방식 |
| 5 | 곁가지 — 흥미롭지만 평가와 연결이 옅음 |

이 척도가 두 곳에서 같은 자로 쓰인다: 오프라인 생성(Grok이 풀 질문에 매김)과
면접 중(모델이 자기 꼬리질문에 매김). 그래서 질문 문장만 보고 판정 가능한 절대
기준이어야 한다. 척도는 툴 docstring이 소유한다 — 모델이 자기 질문에 값을 매길
때 읽는 곳이 거기다.

**문턱 공식은 모델에게 알리지 않는다.** 공식을 알면 통과에 필요한 값을 역산해
신고하게 된다. 모델에게 주는 것은 척도와, 매 호출 돌아오는 `note`뿐이다.

**정렬은 코드 변경이 없다.** `QuestionPool.next`의 `min(key=priority)`가 이미
동점을 리스트 순서(=생성 순서)로 가른다.

### 생성 쪽 검증은 범위만

`generation._validated`에서 `1 ≤ priority ≤ 5`만 본다. 범위를 벗어나면 문턱
계산이 깨지므로 이건 진짜 방어다.

분포는 검사하지 않는다. 값이 한쪽으로 쏠려도 설계가 무너지지 않기 때문이다 —
전부 1이면 문턱이 3→2→1로 빡빡해질 뿐이고(남은 게 다 핵심이면 헤매지 않는 것이
맞다), 전부 5여도 자유 질문 상한 3이 받는다. 개수를 제한하면 값이 더는
"질문마다의 실제 기여도"가 아니게 된다.

고정 질문은 대화 순서가 곧 중요도 순서라 그대로 맞는다: 자기소개 1 · 지원 동기 2 ·
입사 포부 3 · 마지막 한마디 4.

## 세션 상태

`interviewer/tools.py`의 state 키에 하나를 더한다.

| 키 | 뜻 |
|---|---|
| `free_questions` | 마지막 뼈대질문 이후 승인된 모델 자작 질문 수 |

`asked`(배달된 풀 질문 id)와 `stage`는 그대로다. 화면의 "질문 N"은 계속 뼈대질문
번호를 센다 — 자유 질문은 카운터를 올리지 않는다.

## note — 매 턴 갱신되는 지시 채널

프롬프트가 못 하는 일을 여기가 한다. 세 경우 모두 `note`를 채운다.

- **새 주제**: 현행 그대로 (단계 이름 + "그대로 읽지 말고 자연스럽게" + 단계 태그)
- **승인**: 마지막 준비된 질문 이후 자유 질문을 몇 개 했는지 알린다. 모델이 자기
  페이스를 볼 수 있는 유일한 창이다
- **반려**: 왜 넘어가는지 + 단계 안내

## 계측

이 변경의 성적표는 **툴 없이 나간 질문이 있는가**이다. 코드로는 막을 수 없으므로
로그 대조로 확인한다.

- 툴 호출마다 한 줄: `kind`, `tag`, 신고 `priority`, 판정, 문턱, 자유 질문 수, 경과
- 반려는 문턱과 비교값을 같이 남긴다 — 문턱이 실제로 작동했는지 사후에 재구성할
  수 있게
- 기존 `면접관: <전문>` 로그와 대조하면 툴을 거치지 않은 질문이 드러난다

## 테스트

`server/tests/test_ask_question_tool.py` (기존 `test_next_question_tool.py` 확장):

- 새 주제 → 풀 질문이 `ask`에 실리고 카운터 0
- 꼬리질문 승인 → 모델 문장이 `ask`에 그대로, 카운터 증가
- 문턱이 자유 질문 수만큼 올라간다 (0개·1개·2개에서 각각 판정)
- 문턱을 못 넘으면 풀 질문으로 반려되고 카운터가 0으로 돌아간다
- 자유 질문 3개 뒤에는 `priority=1`이어도 반려된다 (상한이 문턱보다 먼저)
- 비교 대상은 태그를 무시하고 뽑는다 — 같은 주제로 되돌아가지 않는다
- 풀이 비면 꼬리질문을 승인한다
- 하드캡 → done / 시간 경과 → 단계 끌어올림 (기존 유지)
- 태그 enum 주입은 기존 테스트 그대로 (`AskQuestionTool`로 이름만 바뀜)

`server/tests/test_generation.py`: 단계 안 priority 분포 검증(1은 하나, 전부 같으면
실패).

`server/tests/test_question_pool.py`: 동점 priority가 생성 순서로 갈린다.

## 남는 위험

**침묵이 늘어난다.** Live API 함수 호출은 순차 전용이라 툴이 도는 동안 소리가
끊긴다. 지금은 새 주제에서만 그랬는데 이제 꼬리질문마다 생긴다. `_STYLE`의
"짧은 반응을 먼저 말하세요"가 그 자리를 메우게 되어 있지만, 실제 체감은 실
연결에서만 판정된다. 이번 변경에서 가장 먼저 확인할 것이다.

**완전 강제가 아니다.** 모델이 툴을 건너뛰고 그냥 말해버리는 것은 막을 수 없다.
이 설계가 강한 이유는 강제가 아니라 툴 선언과 `note`가 매 호출 다시 도착해 지시가
바래지 않는다는 쪽이다.

**기존 준비 데이터 10건의 priority는 옛 뜻(순서)이다.** 값이 1~5 범위 안이고
정렬도 유지되므로 동작은 하지만 중요도로서는 부정확하다. 데모에 쓸 것 하나만
재생성하면 충분하다.
